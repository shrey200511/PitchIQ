## Phase 1: Data pipeline

**What:** download → clean each source → join → `data/processed/matches.parquet` + `fixtures.parquet` + `reports/cleaning_log.md`.

Key code, `merge.py`:
```python
matches = fd.merge(played[[...]], on=["season", "home", "away"], how="left", validate="one_to_one")
gap = (matches["date"] - matches["us_datetime"].dt.normalize()).dt.days.abs()
bad_date = has_us & (gap > DATE_TOLERANCE_DAYS)
```
| Line | What it does | Why |
|---|---|---|
| `merge(..., on=["season","home","away"])` | Joins football-data to Understat on the pairing | A home/away pairing happens exactly once per season, so it's a natural unique key. Dates move (postponements) and Understat stores UTC |
| `how="left"` | Keeps every football-data match | football-data is the record for results and odds; xG is an add-on |
| `validate="one_to_one"` | Raises if a key appears twice on either side | Turns a silent duplication bug into a crash |
| `gap = ...` | Days between the two sources' dates | Uses the date as a *check*, not a key |
| `bad_date = ... > 2` | Flags disagreements, logged in the cleaning log | Surfaces postponed or mismatched games for review |

Other cleaning rules (`clean.py`), all logged with row counts:
- **Dates:** parse `dd/mm/yyyy` *and* `dd/mm/yy` explicitly. Never let pandas guess month-first (3 Feb would become 2 Mar).
- **Result:** recompute H/D/A from goals and log any disagreement with `FTR`.
- **Odds:** row-wise fallback chain Pinnacle → market average → Bet365, with the source recorded per row.
- **Team names:** explicit Understat→football-data map. Unknown names **raise** with the closest suggestions.

- [ ] Read `reports/cleaning_log.md`; note anything odd in `DECISIONS.md`

**Interview Qs**
1. *How did you join two sources with different team names?* "With an explicit mapping table that fails loudly. Fuzzy matching is convenient, but it can silently drop a promoted club's matches. If Understat introduces a name I haven't mapped, the pipeline stops and suggests the closest football-data names."
2. *How did you handle postponed matches?* "I join on season plus home and away team, not date. Each pairing happens once per season, so a postponed game still matches. I keep football-data's actual played date because rest-day features need it, and I log any date gap over two days."

## Phase 2: Team strength (Elo from scratch)

Key code, `ratings/elo.py`:
```python
e = expected_home(rh, ra, params.hfa)                 # 1 / (1 + 10^(-(rh + hfa - ra)/400))
actual = 1.0 if hg[i] > ag[i] else 0.5 if hg[i] == ag[i] else 0.0
g = float(margin_multiplier(hg[i] - ag[i])) if params.use_margin else 1.0
delta = params.k * g * (actual - e)
ratings[h] = rh + delta
ratings[a] = ra - delta
```
| Line | What it does | Why |
|---|---|---|
| `expected_home(...)` | Logistic curve on the rating gap plus home advantage | 400 points of gap ≈ 10:1 odds. HFA adds points to the home side only |
| `actual = 1 / 0.5 / 0` | Converts the result to a score | Elo models expected *score*, so a draw is half a win |
| `margin_multiplier` | 1, 1.5, then (11+gd)/8 | A 4-0 is stronger evidence than a 1-0, but with diminishing returns |
| `delta = k * g * (actual - e)` | Size of the surprise × learning rate | Expected results barely move ratings; upsets move them a lot |
| `+delta / -delta` | Zero-sum update | Rating points are transferred, so the league average is stable |
| (before update) `out_h[i], out_a[i] = rh, ra` | Stores **pre-match** ratings | The feature table only ever sees ratings from before kickoff |

Also: **summer regression** (`season_regress`) pulls ratings toward the mean, because squads change in the off-season. **Promoted teams** start at the relegated teams' average. **Tuning:** grid over K × HFA × regression, scored by MSE of expected score on **2008–2019 only**.

Rolling attack/defence strength lives in Phase 3 as EWM goals/xG for and against. Dixon-Coles (Phase 4) estimates attack/defence as model parameters.

**Checklist**
- [ ] `reports/tuning_elo.csv`: is the best K on a grid edge? (The pipeline warns if so.)
- [ ] Ratings plot in notebook 02 looks sane (title winners near the top)

**Interview Qs**
1. *How did you choose K?* "Grid search over K, home advantage and summer regression, scored by squared error between Elo's expected score and the actual score, on 2008–2019 only. My validation and test seasons played no part in the choice. Mine came out at K = _[your value]_."
2. *How do you handle promoted teams?* "They enter at the average rating of the three teams they replaced. That's the best prior for a team that just came up, and it's better than resetting to 1500, which would rate them as mid-table."
3. *Why tune on expected-score error and not log loss?* "Elo outputs an expected score, not three outcome probabilities. Mapping it to H/D/A needs a separate model, which I do in Elo-logit. Tuning Elo on its own native target keeps the two steps separate."

## Phase 3: Features and the leakage check

Key code, `features/build.py`:
```python
res = pd.merge_asof(left.sort_values("date"), right, on="date", by=["team"] + by_extra,
                    allow_exact_matches=False, direction="backward")
```
| Part | What it does | Why |
|---|---|---|
| `right` = per-team rolling stats **including** each match | e.g. EWM xG after match *n* | Easy to compute and to verify |
| `merge_asof(..., direction="backward")` | For each game, takes the team's latest stats row | "Most recent info about this team" |
| `allow_exact_matches=False` | Excludes rows on the **same date** | A team plays once per day, so this means "finished before kickoff". `True` is the classic leak, and the test suite proves the leakage check catches it |
| `by=["team"]` | Per-team lookup | Each side's own history |

Features: Elo (home, away, diff, expected score); last-5 points; EWM (half-life 6 games) goals, xG and shots on target for/against; venue-specific form; rest days (capped at 14); promoted flag; games played; balance gaps; head-to-head (last 6 meetings).

**Leakage check** (`features/leakage.py`), the perturbation test:
```python
scrambled.loc[future, c] = rng.permutation(vals) + rng.integers(0, 3, len(vals))   # wreck all results from d onward
rebuilt = build_features(scrambled, ...)
diff = ~np.isclose(base.loc[on_day, FEATURES], rebuilt.loc[on_day, FEATURES], equal_nan=True)
```
| Line | What it does | Why |
|---|---|---|
| scramble from date *d* | Destroys every outcome on/after *d* | If a feature for day *d* depends on day-*d* results, it will change |
| rebuild everything | Runs the full feature code again | Tests behaviour, so it catches leaks in code written later too |
| compare day-*d* features | Must be identical | Any difference = leakage, so the test fails |
| `later_features_changed` | Confirms later rows *did* change | Proves the test isn't trivially passing |

**Checklist**
- [ ] `reports/leakage_check.csv` shows `none` / `True` for every date
- [ ] `pytest -k leak` passes, including the deliberate-leak test

**Interview Qs**
1. *How do you know there's no leakage?* "Two ways. By construction: features come from an as-of join that only sees rows strictly before the match date. By test: I scramble every result from a date onward, rebuild all features, and assert that date's features are unchanged. I also inject a deliberately leaky join in the test suite to prove the check catches it."
2. *What's the most common leak in sports models?* "Rolling averages that include the current match, from a missing `shift(1)` or an inclusive date join. Another is using closing odds as a feature when you're predicting days in advance. I keep odds strictly as a benchmark, and a column guard blocks them from the feature list."
3. *Why EWM rather than a simple rolling mean?* "Exponential weighting lets recent games count more without a hard cut-off, and it handles missing xG cleanly. The half-life of six games is a bias-variance trade-off: shorter reacts faster but is noisier."

## Phase 4: Baselines (always-home, base rates, Poisson / Dixon-Coles)

Key code, `models/dixon_coles.py`:
```python
lam = np.exp(mu + home + att[hi] - dfn[ai])        # home expected goals
nu  = np.exp(mu + att[ai] - dfn[hi])               # away expected goals
tau = _tau(x, y, lam, nu, rho)                     # low-score correction
ll  = log(tau) + x*log(lam) - lam - lgamma(x+1) + y*log(nu) - nu - lgamma(y+1)
return -np.sum(w * ll) + penalty
```
| Line | What it does | Why |
|---|---|---|
| `lam = exp(...)` | Home goal rate from attack, opponent defence and home advantage | Log link keeps rates positive; effects multiply |
| `nu = exp(...)` | Away goal rate (no home term) | Same structure for the visitors |
| `tau` | Adjusts P(0-0, 1-0, 0-1, 1-1) via `rho` | Independent Poissons misprice low scores; `rho` captures the dependence |
| `ll` | Poisson log-likelihood of the observed score | Fits teams to actual goals, not just results |
| `w = exp(-xi * days_ago)` | Down-weights old matches (≈1-year half-life) | Teams change; recent games matter more |
| `penalty` | Gaussian prior on strengths | Stops teams with few games (promoted) getting extreme ratings |

Scoreline matrix → P(H) = sum below the diagonal, P(D) = trace, P(A) = sum above. **Walk-forward:** refit every 7 days on data strictly before the block.

**Checklist**
- [ ] Base rates and always-home rows appear in the results table
- [ ] Dixon-Coles `rho` is small and negative on real data (check `dc_predictions.parquet`)

**Interview Qs**
1. *Why Dixon-Coles over plain Poisson?* "Independent Poissons slightly under-predict 0-0 and 1-1. Dixon-Coles adds one parameter, rho, to correct the four low scores, and it down-weights old matches. I report both, so the effect of rho is measured, not assumed."
2. *Why have such simple baselines?* "Base rates show what you get with no information at all. If a complex model can't clearly beat them and Elo-logit, its complexity isn't paying for itself."
3. *How do you get H/D/A from a goals model?* "Build the full scoreline probability grid, 0–10 goals each side, and sum it: below the diagonal is a home win, the diagonal is a draw, above is an away win. Scorelines also give goal difference, which the season simulator needs for tie-breaks."

## Phase 5: ML models with time-based validation

Key code, `models/ml.py` (simplified):
```python
for s in seasons:
    train = table[(table.season >= MODEL_START) & (table.season < s)]
    test  = table[table.season == s]
    model = factory().fit(*xy(train, features))
    p = predict(model, test[features])
    if temperature:
        T = fit_temperature(predict(factory().fit(*xy(train[train.season < s-1])), Xv), yv)
        p = apply_temperature(p, T)
```
| Line | What it does | Why |
|---|---|---|
| `season < s` | Trains only on the past | No future information in training |
| `season == s` | Predicts one whole season | Matches the real use case |
| `fit_temperature` on season *s−1* | Learns one scalar T on data the inner model never saw | Calibration fitted in-sample would be useless |
| `apply_temperature` | Softmax(log p / T) | T > 1 softens overconfidence; one parameter can't overfit |

Logistic regression pipeline: median imputation + missing-indicators → standardise → multinomial LR (C tuned). LightGBM: shallow trees (7–15 leaves), ≥ 40 samples per leaf, row/column subsampling. Both tuned by **validation log loss only**.

**Checklist**
- [ ] `reports/tuning_*.csv` reviewed; best LightGBM config isn't at a grid edge
- [ ] Logistic regression vs LightGBM: which wins on validation? Write it in `DECISIONS.md`

**Interview Qs**
1. *Why not a random train/test split?* "Matches are time-ordered and team strength drifts. A random split lets the model train on March to predict February, so it learns future form. I use walk-forward: each season is predicted by a model trained only on earlier seasons."
2. *Why does LightGBM sometimes lose to logistic regression here?* "With roughly 3,800 training matches and noisy outcomes, most of the signal is close to linear in a few strength measures, like Elo and xG difference. Trees can overfit the noise. I'll say which won on my data and by how much: _[your numbers]_."
3. *What is temperature scaling?* "One parameter that rescales the model's log-probabilities. If the model is overconfident, T > 1 flattens its probabilities. I fit it on a season the model never trained on, so it corrects real overconfidence rather than memorising."

## Phase 6: Evaluation vs the market

Key code, `evaluation/metrics.py`:
```python
q = 1.0 / odds                                     # implied probabilities, sum > 1
prop = q / q.sum(axis=1, keepdims=True)            # proportional margin removal
# Shin: solve z so that sum_i (sqrt(z^2 + 4(1-z) q_i^2 / B) - z) / (2(1-z)) = 1
```
| Line | What it does | Why |
|---|---|---|
| `1/odds` | Raw implied probabilities | They sum to ~1.02–1.06; the excess is the bookmaker's margin (overround) |
| proportional | Divide by the sum | Simple; assumes margin is spread in proportion to probability |
| Shin | Solves for the "insider" share z | Puts more margin on longshots (favourite–longshot bias), usually a better true-probability estimate |

Metrics: **log loss** (selection metric), **Brier**, **RPS** (respects H > D > A order), **accuracy**, **ECE** + reliability plots. All models are scored on the *same* matches. A **paired bootstrap** gives a 95% CI for each model's log-loss gap to the closing market.

**Checklist**
- [ ] `reports/results.md` test table filled into README
- [ ] Bootstrap CI read honestly: does it include 0?
- [ ] Reliability plot: is any model systematically over-confident?

**Interview Qs**
1. *How do you remove the bookmaker margin?* "1/odds gives implied probabilities that sum to more than one; the excess is the overround. Proportional normalisation divides by the sum. Shin's method assumes the bookmaker protects against insiders, which puts more margin on longshots. That matches the known favourite–longshot bias. I report both; Shin is my reference."
2. *Did you beat the bookmakers?* "_[Answer from your bootstrap table.]_ The honest framing: the closing line includes team news and money from sharp bettors. My model only sees public history. The useful question is how big the gap is and where it comes from, like early-season matches or promoted teams."
3. *Why log loss rather than accuracy?* "Accuracy only checks the top pick. A model saying 40/30/30 and one saying 90/5/5 get the same accuracy if the favourite wins. Log loss rewards being right *and* honest about uncertainty, and it punishes confident misses heavily."

## Phase 7: Draws

`analysis/draws.py` produces `reports/figures/draws.png` and the draws section of `results.md`.

| Analysis | What it shows |
|---|---|
| Draw is argmax % | How often any model picks a draw (usually ≈ 0%) |
| Mean predicted vs actual draw rate | Calibration of P(draw) |
| Draw rate by \|Elo diff\| and expected-goals quintile | Draws cluster in even, low-scoring games |
| Dixon-Coles vs Poisson draw Brier | Whether the rho correction helps the draw probability |
| Draw threshold rule | Calling "draw" when P(D) ≥ t: recall goes up, accuracy usually goes down |

**Interview Qs**
1. *Why are draws hard?* "Even a perfectly balanced match is roughly 37/26/37, so a draw is rarely the single most likely result. Models almost never pick it, even when their draw probabilities are well calibrated. The problem is the decision rule, not necessarily the probabilities."

3. *Should you optimise for draw recall?* "Only if the use case values it. For probability quality, log loss and calibration matter. A threshold rule changes the decision, not the forecast."

## Phase 9: Season simulator

Key code, `simulate/season.py` (simplified):
```python
thetas = rng.multivariate_normal(params._theta, _psd(params.cov), size=200)   # strength uncertainty
idx = (cum[:, None, :] < u[:, :, None]).sum(axis=2)                         # sample scorelines
hg, ag = idx // g, idx % g
key = pts * 1e6 + (gd + 500) * 1e3 + gf + tiny_random                         # PL tie-break order
```
| Line | What it does | Why |
|---|---|---|
| `multivariate_normal(theta, cov)` | 200 plausible sets of team strengths | We don't know strengths exactly; without this, title odds are overconfident |
| inverse-CDF sampling | Draws a scoreline per fixture per simulation, vectorised | Fast enough for 10,000 seasons |
| `idx // g, idx % g` | Flat index → (home goals, away goals) | Scorelines give goal difference |
| sort key | Points, then GD, then goals scored | Premier League tie-break order |

Remaining fixtures = all home/away pairings not yet played. A double round-robin means no calendar is needed.

**Interview Qs**
1. *Why simulate with a goals model, not your best classifier?* "Ties on points are broken by goal difference, so I need scorelines. Dixon-Coles generates them coherently."
2. *How did you avoid overconfident title odds?* "I sample team strengths from the fitted model's uncertainty (normal approximation, inverse Hessian) and run 50 seasons for each of 200 draws. Fixed strengths ignore that we're unsure about them, and that understates the chance of surprises."
3. *How would you validate the simulator?* "Run it from the same point in past seasons and score the predicted final positions, e.g. Brier on 'finishes top 4'. That's the natural next step."
